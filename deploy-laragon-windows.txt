Anda sudah punya: Laragon, Node, Git, PHP 8.2, MySQL 8.4.3, phpMyAdmin.
Itu sudah cukup. Tidak ada yang perlu dipasang lagi.

Yang belum ada hanyalah PENGATURAN — dan empat di antaranya adalah hal yang

================================================================================
 0. TIGA HAL YANG BIKIN GAGAL DI JARINGAN — BACA INI DULU
================================================================================

 Kabar baiknya: `composer run dev` MEMANG menjalankan semuanya sekaligus —
 web, antrean, dan penjadwal. Tidak perlu Apache, tidak perlu Task Scheduler.
 Hanya ada satu masalah, dan sudah diperbaiki: lihat nomor 1.

 1. PAKAI `composer run dev:lan`, BUKAN `composer run dev`.
    Script `dev` bawaan mengikat ke 127.0.0.1, yang artinya "hanya komputer
    ini" — dari HP seWiFi alamatnya tidak menjawab sama sekali. Sudah
    ditambahkan script kedua, `dev:lan`, yang isinya sama persis tetapi
    mengikat ke 0.0.0.0 (semua alamat).

    Diukur di komputer ini:
       port 5566 dengan `dev`      -> LocalAddress 127.0.0.1 -> dari IP LAN GAGAL
       port 5567 dengan --host=0.0.0.0 -> LocalAddress 0.0.0.0 -> dari IP LAN HTTP 200

    `dev` sengaja dibiarkan apa adanya supaya laptop pengembang tidak
    diam-diam terbuka ke jaringan sekitar. Yang membuka ke jaringan adalah
    keputusan sadar, dengan perintah yang berbeda.

 2. APP_URL HARUS ALAMAT IP, BUKAN localhost.
    Logo, favicon, dan lampiran tiket dibuatkan alamat dari APP_URL
    (config/filesystems.php: 'url' => env('APP_URL').'/storage'). Kalau APP_URL
    masih http://localhost, maka di HP penguji semua gambar itu menunjuk ke
    localhost MILIK HP ITU SENDIRI — jadi gambar rusak semua, padahal di
    komputer server terlihat normal.

 3. KOMPUTER SERVER TIDAK BOLEH SLEEP.
    Windows tidur = server mati, penjadwal mati, antrean mati. Tidak ada pesan
    apa pun. Lihat bagian 7.

 CATATAN SOAL KECEPATAN (angka nyata, bukan perkiraan)
    Server bawaan PHP memproses permintaan bergiliran. Diukur di komputer ini,
    halaman /students dengan 7.392 mahasiswa:

        1 permintaan                        0,53 detik
        3 orang klik bersamaan   total 1,2 detik
        6 orang klik bersamaan   total 2,2 detik
       12 orang klik bersamaan   total 4,0 detik
       20 orang klik bersamaan   total 6,5 detik      (semua berhasil, 0 error)

    Artinya: untuk 5–10 penguji yang membuka halaman dengan kecepatan manusia
    biasa, `composer run dev:lan` sudah cukup dan tidak akan terasa lambat.
    Yang menunggu lama hanya kalau belasan orang menekan tombol pada detik
    yang sama persis.

    Kalau nanti dipakai puluhan orang sehari-hari, barulah pindah ke Apache
    (bagian 3C) — itu peningkatan, bukan syarat.

 2. DATABASE
================================================================================

 Lewat phpMyAdmin (http://localhost/phpmyadmin), buat database baru:

     Nama      : utsosmed
     Collation : utf8mb4_unicode_ci

 Lalu isi di .env:

     DB_CONNECTION=mysql
     DB_HOST=127.0.0.1
     DB_PORT=3306
     DB_DATABASE=utsosmed
     DB_USERNAME=root
     DB_PASSWORD=<<< LIHAT DI BAWAH — INI SERING SALAH >>>

 PASSWORD ROOT: TERGANTUNG MySQL MANA YANG DIPAKAI
 ------------------------------------------------------------------------------
   MySQL BAWAAN LARAGON      -> root TANPA password. Biarkan DB_PASSWORD kosong.
   MySQL DIINSTAL SENDIRI    -> root PUNYA password. Installer MySQL menanyakan
   (mis. MySQL 8.4.3 dari       password root saat pemasangan. Isikan password
    installer resmi)            itu ke DB_PASSWORD.

   Kalau dua-duanya terpasang, yang menjawab di port 3306 adalah yang servisnya
   jalan duluan — dan itu belum tentu yang Anda kira.

 CARA MEMASTIKAN, sebelum menjalankan aplikasi:

     mysql -u root -p -h 127.0.0.1 -e "select current_user(), version();"

   Diminta password lalu berhasil -> isi password itu ke DB_PASSWORD
   Berhasil dengan ENTER kosong   -> DB_PASSWORD dibiarkan kosong
   ERROR 1698 / 1045              -> password salah; lihat bagian 11

 DISARANKAN: JANGAN PAKAI root
 ------------------------------------------------------------------------------
 Buat user khusus aplikasi. Kalau passwordnya bocor, yang terbuka hanya satu
 database, bukan seluruh MySQL. Lewat phpMyAdmin > User accounts > Add user
 account, atau lewat terminal:

     mysql -u root -p
       CREATE DATABASE utsosmed CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
       CREATE USER 'utsosmed'@'localhost' IDENTIFIED BY 'PasswordKuat123';
       CREATE USER 'utsosmed'@'127.0.0.1' IDENTIFIED BY 'PasswordKuat123';
       GRANT ALL PRIVILEGES ON utsosmed.* TO 'utsosmed'@'localhost';
       GRANT ALL PRIVILEGES ON utsosmed.* TO 'utsosmed'@'127.0.0.1';
       FLUSH PRIVILEGES;

   Dua baris user itu memang perlu keduanya: MySQL menganggap 'localhost'
   (lewat socket/pipe) dan '127.0.0.1' (lewat TCP) sebagai HOST BERBEDA, dan
   Laravel memakai 127.0.0.1.

   Lalu di .env:
       DB_USERNAME=utsosmed
       DB_PASSWORD=PasswordKuat123

 CATATAN MySQL 8.4: versi ini menghapus dukungan mysql_native_password secara
 bawaan. Laravel tidak bermasalah dengan itu. Tapi kalau muncul error
 "authentication plugin cannot be loaded", buat user baru dengan autentikasi
 caching_sha2_password dan pakai user itu.

 Kemudian:

     php artisan migrate --force
     php artisan db:seed --class=RolePermissionSeeder --force
     php artisan db:seed --class=RegionSeeder --force
     php artisan db:seed --class=TicketCategorySeeder --force
     php artisan storage:link

 JANGAN jalankan `php artisan db:seed` polos. Perintah itu membuat 14 akun
 berpassword "password". Lihat bagian 8.

 CATATAN storage:link DI WINDOWS: perintah ini membuat symbolic link, dan
 Windows butuh izin khusus. Kalau gagal:
   - Buka Terminal Laragon sebagai Administrator, lalu ulangi, ATAU
   - Aktifkan Developer Mode (Settings > Update & Security > For developers)
 Kalau tetap gagal, salin manual: buat folder C:\laragon\www\schedule-sosmed\
 public\storage dan isi dengan isi storage\app\public. (Cara ini tidak ikut
 ter-update otomatis, jadi symlink lebih baik.)

 3. MEMBUAT KOMPUTER INI BISA DIAKSES LEWAT WIFI
================================================================================

 3.1  CARI ALAMAT IP KOMPUTER SERVER

      Buka Command Prompt, ketik:

          ipconfig

      Cari baris "IPv4 Address" pada adapter WiFi (atau Ethernet kalau pakai
      kabel). Contoh: 192.168.1.10

      Alamat inilah yang nanti dibuka penguji: http://192.168.1.10

 3.2  KUNCI IP-NYA SUPAYA TIDAK BERUBAH

      IP dari WiFi biasanya berubah sendiri setelah beberapa jam atau setelah
      restart. Kalau berubah, semua penguji kehilangan akses tanpa sebab yang
      jelas. Dua cara:

      A. (Lebih baik) Di router: fitur "DHCP Reservation" / "Static Lease" —
         ikat MAC address komputer server ke satu IP tetap.

      B. Di Windows: Settings > Network & Internet > WiFi > pilih jaringan >
         IP assignment > Edit > Manual > isi IP, subnet 255.255.255.0,
         gateway = IP router, DNS = IP router.
         Pilih IP di luar rentang DHCP router supaya tidak bentrok.

 ------------------------------------------------------------------------------
 3A. CARA UTAMA — `composer run dev:lan`  (ini yang dipakai)
 ------------------------------------------------------------------------------

      cd C:\laragon\www\schedule-sosmed
      composer run dev:lan

      Satu perintah, tiga proses sekaligus, dan bisa diakses dari WiFi:

         server  -> php artisan serve --host=0.0.0.0 --port=5566
         queue   -> php artisan queue:listen --tries=1     (untuk import Excel)
         cron    -> php artisan schedule:work              (pengganti cron)

      Penguji membuka: http://192.168.1.10:5566

      Biarkan jendela terminalnya TERBUKA selama validasi. Menutupnya
      mematikan ketiganya sekaligus (memang begitu desainnya: --kill-others).

      Kalau salah satu proses mati, semuanya ikut berhenti — itu disengaja,
      supaya tidak ada keadaan setengah jalan yang membingungkan. Jalankan
      ulang perintahnya.

 ------------------------------------------------------------------------------
 3B. MENGGANTI PORT (atau host) — CUKUP DI .env
 ------------------------------------------------------------------------------

      Port TIDAK lagi ditanam di composer.json. `php artisan serve` membacanya
      dari .env, jadi satu tempat saja:

          SERVER_HOST=127.0.0.1     # 0.0.0.0 supaya bisa diakses dari jaringan
          SERVER_PORT=5566          # ganti ke 8000 atau berapa pun

      Ingin pindah ke 8000? Ubah satu baris:

          SERVER_PORT=8000

      lalu jalankan ulang `composer run dev:lan`. Alamatnya jadi
      http://192.168.1.10:8000 — dan jangan lupa APP_URL (3.4) serta aturan
      firewall (3.3) ikut disesuaikan ke port yang baru.

      Diuji: dengan SERVER_PORT=5571 dan tanpa flag apa pun, `php artisan serve`
      membuka 127.0.0.1:5571. Jadi nilainya benar-benar terbaca dari .env.

      Kalau port bentrok dengan aplikasi lain, `artisan serve` otomatis mencoba
      port berikutnya (5567, 5568, …) dan menuliskan port yang akhirnya dipakai
      di terminal. Perhatikan baris "Server running on" saat start.

      Menjalankan manual di tiga terminal terpisah juga boleh:

         php artisan serve --host=0.0.0.0 --port=8000
         php artisan queue:work
         php artisan schedule:work

 ------------------------------------------------------------------------------
 3C. OPSIONAL — APACHE LARAGON (kalau nanti dipakai puluhan orang)
 ------------------------------------------------------------------------------

      Apache melayani banyak permintaan sekaligus dan jalan sebagai layanan,
      jadi tidak bergantung pada jendela terminal yang terbuka. Ini BUKAN
      syarat untuk hari validasi.

      1. Menu Laragon > Apache > httpd.conf, arahkan DocumentRoot ke
            "C:/laragon/www/schedule-sosmed/public"

      2. Menu Laragon > Stop All, lalu Start All.

      3. Penguji membuka http://192.168.1.10  (tanpa :5566)

      4. Antrean dan penjadwal TETAP harus dijalankan sendiri — Apache hanya
         melayani web. Buka dua terminal:
            php artisan queue:work
            php artisan schedule:work
         atau pasang Task Scheduler (bagian 6).

 3.3  IZINKAN LEWAT WINDOWS FIREWALL

      Ini langkah yang paling sering terlupa. Tanpa ini, dari komputer server
      bisa dibuka, dari HP tidak bisa sama sekali.

      Buka PowerShell SEBAGAI ADMINISTRATOR:

          New-NetFirewallRule -DisplayName "UT Sosmed HTTP" -Direction Inbound `
              -Protocol TCP -LocalPort 80 -Action Allow -Profile Private

      Untuk cara 3A (composer run dev:lan) portnya 5566:

          New-NetFirewallRule -DisplayName "UT Sosmed 5566" -Direction Inbound `
              -Protocol TCP -LocalPort 5566 -Action Allow -Profile Private

      Untuk cara 3C (Apache) portnya 80, seperti perintah di atas.

      CATATAN: mengikat ke 0.0.0.0 saja TIDAK cukup. Itu membuat aplikasi mau
      menerima dari jaringan; firewall Windows-lah yang memutuskan boleh atau
      tidak. Keduanya harus beres.

      -Profile Private artinya hanya berlaku di jaringan yang ditandai
      "Private". Pastikan WiFi kantor ditandai Private, bukan Public:
      Settings > Network & Internet > WiFi > klik nama jaringan >
      Network profile > Private.

 3.4  SETEL APP_URL — JANGAN DILEWAT

      Di .env:

          APP_URL=http://192.168.1.10

      (pakai :5566 kalau memakai cara 3A, tanpa port kalau memakai Apache)

      Lalu WAJIB:

          php artisan config:clear

      Tanpa ini, logo dan lampiran rusak di semua perangkat selain komputer
      server. Lihat bagian 0 nomor 3.

 3.5  UJI DARI HP

      Sambungkan HP ke WiFi yang sama, buka http://192.168.1.10
      Harus muncul halaman login.

      Kalau tidak bisa:
        - Ping dulu dari HP (pakai aplikasi ping) atau dari laptop lain:
              ping 192.168.1.10
          Tidak membalas  -> masalah jaringan/isolasi WiFi, bukan aplikasi
          Membalas        -> masalah firewall atau Apache
        - Sebagian router punya fitur "AP Isolation" / "Client Isolation" yang
          memblokir perangkat saling terhubung. Matikan di pengaturan router.


================================================================================
 3.6  BERAPA BERAT SEBENARNYA — SUPAYA TIDAK SALAH KHAWATIR
================================================================================

 Sistem ini dipakai internal, maksimal sekitar 10 orang, untuk mengelola
 konten. Yang banyak bukan jumlah pengguna, melainkan scraping, komentar, dan
 penilaian AI. Dua beban itu berjalan di TEMPAT YANG BERBEDA, dan itu kabar
 baik:

   HALAMAN WEB  <- yang dipakai 10 orang
      Ringan. Diukur: 0,5 detik per halaman; 12 orang klik bersamaan selesai
      dalam 4 detik, tanpa error. 10 orang yang membuka halaman dengan
      kecepatan manusia biasa tidak akan pernah menunggu.

   SCRAPING & AI  <- yang volumenya besar
      TIDAK lewat halaman web, dan TIDAK lewat antrean. Semuanya berjalan di
      dalam proses `schedule:work` (kolom "cron" di composer run dev:lan):

        tiap menit    metrik akun
        tiap jam      insight postingan, cache gambar, cocokkan kontak
        tiap 15 menit klasifikasi AI — maksimum 200 interaksi per putaran
        tiap 5 jam    sinkron komentar Instagram

      Artinya panggilan AI yang lambat memperlambat PENJADWAL, bukan halaman
      yang sedang dibuka orang. Aplikasinya tetap responsif.

   ANTREAN (queue)  <- hanya import Excel
      Import data mahasiswa saja. Jarang dipakai, tapi harus tetap hidup atau
      import berhenti di status "menunggu".

 KAPASITAS KLASIFIKASI AI
   200 interaksi per 15 menit = sekitar 800 per jam = sekitar 19.000 per hari.
   Jauh di atas kebutuhan. Kalau suatu saat tunggakannya menumpuk, naikkan
   `crm.ai.per_run_limit` — tapi perhatikan batas kuota Groq, bukan kecepatan
   komputernya, yang biasanya jadi penghalang duluan.

   Cek tunggakan kapan saja:
       php artisan tinker --execute="echo App\Models\Interaction::whereNull('ai_classified_at')->count();"

 KESIMPULAN: untuk 10 orang, `composer run dev:lan` sudah lebih dari cukup.
 Apache (3C) baru relevan kalau nanti dipakai puluhan orang bersamaan.

 6. CRON DI WINDOWS — TASK SCHEDULER (untuk pemakaian tetap)
================================================================================

 `schedule:work` mati kalau jendelanya ditutup atau komputer di-restart. Untuk
 server yang dipakai terus, pakai Task Scheduler supaya jalan sendiri tanpa
 ada yang login.

 6.1  BUAT FILE BANTU
      Buat C:\laragon\www\schedule-sosmed\run-scheduler.bat berisi:

          @echo off
          cd /d C:\laragon\www\schedule-sosmed
          C:\laragon\bin\php\php-8.2.x\php.exe artisan schedule:run

      (sesuaikan nama folder php-8.2.x dengan yang ada di komputer Anda —
       cek di C:\laragon\bin\php\)

      Dan run-queue.bat berisi:

          @echo off
          cd /d C:\laragon\www\schedule-sosmed
          C:\laragon\bin\php\php-8.2.x\php.exe artisan queue:work --stop-when-empty --tries=3

 6.2  DAFTARKAN DI TASK SCHEDULER
      Buka "Task Scheduler" > Create Task (bukan Create Basic Task).

      Tab General:
        Name        : UT Sosmed Scheduler
        [v] Run whether user is logged on or not
        [v] Run with highest privileges

      Tab Triggers > New:
        Begin the task   : On a schedule
        Daily, recur every 1 days
        [v] Repeat task every : 1 minute
            for a duration of : Indefinitely

      Tab Actions > New:
        Action  : Start a program
        Program : C:\laragon\www\schedule-sosmed\run-scheduler.bat

      Tab Settings:
        [v] Run task as soon as possible after a scheduled start is missed
        [ ] Stop the task if it runs longer than...   (HILANGKAN centangnya)

      Ulangi seluruhnya untuk run-queue.bat dengan nama "UT Sosmed Queue".

 6.3  UJI
      Klik kanan task > Run. Lalu buka Dashboard aplikasi, panel "Otomasi"
      harus berbunyi "Otomasi berjalan normal" dalam 1 menit.

 8. AKUN & PASSWORD

 8.1  BUAT ADMIN SENDIRI (jangan pakai db:seed polos)

      php artisan tinker

        $role = App\Models\Role::where('name','super_admin')->first();
        $u = new App\Models\User;
        $u->fill(['name'=>'Nama Admin','email'=>'admin@institusi.ac.id',
                  'password'=>'PASSWORD-PANJANG-YANG-KUAT']);
        $u->role_id = $role->id;
        $u->is_active = true;
        $u->save();

      Akun berikutnya dibuat lewat menu Pengguna di aplikasi.

 8.2  MENEMPEL HASH BCRYPT DARI GENERATOR ONLINE — SUDAH DIDUKUNG

      Di kolom "Kata sandi" (menu Pengguna, dan di tinker seperti di atas),
      Anda boleh menempel hash bcrypt yang sudah jadi, bukan kata sandinya:

          $2y$10$...   (60 karakter)
          $2a$10$...   <- yang paling umum dari generator online
          $2b$12$...

      Aplikasi menyimpannya apa adanya, TIDAK di-hash dua kali, dan pemilik
      akun bisa login dengan kata sandi aslinya.

      Catatan penting:
        - Tempel string yang SAMA PERSIS di kolom "Kata sandi" dan "Ulangi
          kata sandi". Dua hash dari kata sandi yang sama akan berbeda (salt-nya
          acak), jadi kalau Anda men-generate dua kali, form akan menolak.
        - Kalau tertempel sebagian saja, form MENOLAK dengan pesan jelas —
          tidak akan menyimpannya diam-diam sebagai kata sandi biasa.
        - Prefix $2a$/$2b$ otomatis dinormalkan ke $2y$. Digest-nya tidak
          berubah sama sekali; ini hanya penanda versi.

      Pertimbangan keamanan, sekali saja: mengetik kata sandi asli ke situs
      generator pihak ketiga berarti situs itu tahu kata sandi Anda. Untuk akun
      uji coba tidak masalah. Untuk akun asli, lebih baik ketik langsung di
      form aplikasi — hasilnya sama.

DUA MODE SINKRON — PENTING
--------------------------------------------------------------------------------

Perintah di atas berjalan dalam mode SEGARKAN: selalu mulai dari postingan
TERBARU. Itu benar untuk pemakaian harian, karena komentar baru muncul di
postingan baru. Tapi mode ini tidak akan pernah sampai ke postingan lama —
dijalankan seratus kali pun, yang disentuh postingan yang itu-itu juga.

Untuk menarik seluruh riwayat akun, pakai mode LANJUT. Tiap run menyambung dari
posisi run sebelumnya, jadi dijalankan berulang = maju, bukan mengulang:

  php artisan accounts:sync-insights --lanjut              # 1 halaman = 50 postingan
  php artisan accounts:sync-insights --lanjut --halaman=5  # 250 postingan sekali jalan

  php artisan accounts:sync-comments --lanjut              # 40 postingan berikutnya
  php artisan accounts:sync-comments --lanjut --putaran=5  # 5 x 40 = 200, ada jeda

Keduanya mencetak kemajuan, misalnya "Cakupan sekarang: 240 / 2.227". Kalau
sudah habis, perintahnya bilang sendiri dan berhenti.

Jendela usia (INSTAGRAM_MAX_AGE_DAYS, default 90 hari) hanya berlaku di mode
segarkan. Mode --lanjut sengaja mengabaikannya — justru menembus ke belakang
itulah tujuannya.

Backfill ini juga sudah dijadwalkan otomatis (lihat routes/console.php):
insights 2 halaman tiap 6 jam, komentar 40 postingan tiap 2 jam. Jadi kalau
scheduler jalan, riwayat akan terisi sendiri dalam beberapa hari tanpa
diketik manual.

--------------------------------------------------------------------------------
CLOUDFLARE TUNNEL (supaya konten terjadwal bisa terbit)
--------------------------------------------------------------------------------

TUJUANNYA APA

Instagram harus bisa MENGUNDUH file gambar dari internet. Hanya itu. Aplikasi
ini sendiri tidak perlu dibuka ke internet -- dan sebaiknya memang tidak, karena
di dalamnya ada data mahasiswa.

Jadi yang dibuka hanya satu alamat untuk folder media:

    https://media.domain-anda.ac.id/storage/...   -> dibuka ke internet
    http://10.15.10.221:5566                      -> tetap di jaringan kantor

Aplikasi sudah disiapkan untuk pemisahan ini. Dua pengaturan .env:

    FILESYSTEM_PUBLIC_URL   alamat publik untuk media (dipakai Instagram)
    APP_URL                 alamat aplikasi (biarkan alamat lokal)

LANGKAH

 1. Pasang cloudflared di komputer server

        winget install --id Cloudflare.cloudflared

 2. Login dan buat tunnel (sekali saja)

        cloudflared tunnel login
        cloudflared tunnel create sosmed-ut

    Catat Tunnel ID yang muncul.

 3. Arahkan subdomain ke tunnel

        cloudflared tunnel route dns sosmed-ut media.domain-anda.ac.id

    Domainnya harus sudah dikelola Cloudflare (nameserver-nya mengarah ke
    Cloudflare).

 4. Buat file konfigurasi

    C:\Users\<user>\.cloudflared\config.yml

        tunnel: sosmed-ut
        credentials-file: C:\Users\<user>\.cloudflared\<TunnelID>.json

        ingress:
          # HANYA folder media yang dilayani.
          - hostname: media.domain-anda.ac.id
            path: ^/storage/.*
            service: http://127.0.0.1:5566
          # Sisanya ditolak -- halaman aplikasi tidak ikut terbuka.
          - service: http_status:404

    Aturan `path` itu yang menjaga data mahasiswa tetap di dalam. Tanpa baris
    itu, SELURUH aplikasi ikut terbuka ke internet.

 5. Isi .env di komputer server

        FILESYSTEM_PUBLIC_URL=https://media.domain-anda.ac.id/storage

    APP_URL JANGAN diubah -- biarkan alamat lokal.

        php artisan config:clear

 6. Jalankan tunnel sebagai layanan Windows (supaya hidup terus)

        cloudflared service install
        Start-Service cloudflared

 7. Periksa

        php artisan content:check-publish

    Harus berbunyi "SIAP -- konten terjadwal bisa terbit otomatis".

    Lalu uji dari luar jaringan kantor (pakai data HP, matikan WiFi):

        https://media.domain-anda.ac.id/storage/  -- gambar harus terbuka
        https://media.domain-anda.ac.id/dashboard -- HARUS 404

    Baris kedua itu pemeriksaan keamanannya. Kalau dashboard-nya terbuka,
    aturan `path` di config.yml belum benar.

PILIHAN B: SELURUH APLIKASI LEWAT DOMAIN (bisa domain DAN IP sekaligus)

Ini yang dipakai kalau ingin lepas dari alamat IP: staf membuka domain, dan
alamat IP tetap bisa dipakai di dalam kantor. Keduanya melayani dari satu
pemasangan yang sama.

    https://utpkpinsight.my.id        dari mana saja
    http://10.15.10.221:5566          di dalam kantor

  config.yml -- tanpa baris `path`, jadi seluruh aplikasi dilayani:

        ingress:
          - hostname: utpkpinsight.my.id
            service: http://127.0.0.1:5566
          - service: http_status:404

  .env di komputer server:

        APP_ENV=production
        APP_DEBUG=false
        APP_URL=https://utpkpinsight.my.id

        # Kosongkan: media ikut APP_URL, dan APP_URL sudah publik.
        FILESYSTEM_PUBLIC_URL=

        # DUA BARIS BERIKUT MENENTUKAN APAKAH AKSES LEWAT IP MASIH BISA LOGIN.
        SESSION_DOMAIN=null
        # SESSION_SECURE_COOKIE  -> JANGAN diisi sama sekali

  Lalu:  php artisan config:clear

  KENAPA DUA BARIS SESI ITU PENTING

    SESSION_SECURE_COOKIE=true membuat cookie hanya dikirim lewat HTTPS. Akses
    lewat http://10.15.10.221:5566 jadi TIDAK BISA LOGIN -- dan tidak ada pesan
    error apa pun; setiap halaman sekadar kembali ke form login. Dibiarkan
    kosong, cookie otomatis aman saat lewat HTTPS dan tetap bekerja saat lewat
    HTTP di jaringan kantor.

    SESSION_DOMAIN yang diisi domain membuat cookie terikat ke domain itu, dan
    tidak pernah dikirim ke alamat IP. Biarkan null.

  YANG PERLU DISADARI

    Gambar dilayani dari DOMAIN untuk semua orang, termasuk pengunjung dari
    dalam kantor. Jadi kalau internet mati: halaman tetap terbuka lewat IP,
    tapi thumbnail-nya kosong. Isinya tetap bisa dikerjakan.

  KEAMANAN -- BACA INI

    Tanpa baris `path`, SELURUH aplikasi terbuka ke internet: siapa pun yang
    tahu alamat utpkpinsight.my.id sampai ke halaman login. Di dalamnya ada
    NIM, nomor HP, dan alamat mahasiswa, dan yang menjaganya hanya kata sandi.

    Pasang CLOUDFLARE ACCESS di depannya. Gratis sampai 50 pengguna, dan
    menambah satu lapis login Cloudflare sebelum aplikasi bisa disentuh:

        Cloudflare Zero Trust > Access > Applications > Add an application
        Self-hosted, domain: utpkpinsight.my.id
        Policy: Emails -> daftar email staf

    Setelah itu orang luar tidak bisa mencapai halaman login sama sekali.

  Aplikasi sudah memercayai header X-Forwarded-* dari loopback, jadi HTTPS
  terdeteksi benar dan tautan yang dihasilkan tidak jadi http://.

CATATAN

    - Tunnel harus HIDUP saat jadwal terbit tiba. Kalau mati, Instagram tidak
      bisa mengambil gambarnya dan konten ditandai gagal.
    - trycloudflare.com (tanpa domain sendiri) bisa untuk uji coba, tapi
      alamatnya berganti setiap kali dijalankan -- tidak cocok untuk jadwal.

--------------------------------------------------------------------------------
KALAU KOMPUTER MATI, LALU DINYALAKAN LAGI
--------------------------------------------------------------------------------

Jawaban singkat: cukup `composer run dev:lan`. Tidak ada command sinkron yang
wajib diketik manual.

Yang perlu diketahui:

1. Penjadwal TIDAK mengejar ketinggalan.
   `schedule:work` menilai "apa yang jatuh tempo menit ini", bukan "apa yang
   terlewat kemarin". Jadi kalau komputer mati 2 hari, dua hari itu memang
   tidak dikerjakan. Tapi tidak ada yang hilang permanen -- begitu hidup lagi:

     - metrik akun     : jalan dalam 1 menit
     - insights terbaru: jalan di jam berikutnya
     - komentar terbaru: jalan dalam <= 5 jam
     - backfill riwayat: menyambung dari posisi terakhir, bukan mengulang

   Kalau tidak sabar menunggu, satu perintah ini menyegarkan yang penting:

     php artisan accounts:sync-today

2. YANG PERLU DIPERIKSA: konten terjadwal yang lewat waktu.
   Ini satu-satunya hal yang bisa benar-benar rugi. Konten yang seharusnya
   terbit selagi komputer mati akan terlambat. Batas amannya 24 jam
   (config publishing.max_delay_hours). Lewat dari itu, `schedules:prune`
   menandainya GAGAL supaya tidak tiba-tiba terbit di waktu yang salah, dan
   harus dijadwalkan ulang manual.

   Setelah mati lebih dari sehari, periksa:

     php artisan schedules:prune --dry-run

   Tidak mengubah apa pun, hanya menampilkan mana yang kedaluwarsa.

3. Dashboard sudah memberi tahu kalau penjadwal mati.
   Ada heartbeat tiap menit; lewat 5 menit tanpa denyut, dashboard menyebutnya.
   Jadi tidak perlu menebak apakah `schedule:work` masih hidup.

4. Ketiga proses mati bersamaan.
   `composer run dev:lan` memakai --kill-others: kalau satu proses mati, dua
   lainnya ikut mati. Ini disengaja (supaya tidak ada keadaan setengah jalan
   yang menyesatkan), tapi artinya jendela itu tidak boleh ditutup. Untuk
   komputer yang menyala 24 jam dan tidak ada yang login, pakai Task Scheduler
   -- lihat bagian 6.

5. Antrean tidak hilang saat mati.
   Queue-nya di database (tabel `jobs`), bukan di memori. Job yang belum sempat
   dikerjakan tetap ada dan langsung diproses begitu worker hidup lagi.
